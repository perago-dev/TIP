First review

A duplicate-invoice guard that doesn't guard, and a money-parsing bug at scale

TIP's SuiteScript is a set of large, single-purpose integration Map/Reduce jobs that turn incoming JSON payloads into journal entries, cash sales, and customer payments for a school's enrollment/billing system. Two real defects stand out. First, Production's duplicate-invoice guard — the User Event whose entire job is to stop a second invoice from being created against the same enrollment reference — detects the duplicate, writes an error record, and then lets the save proceed anyway, because the throw that should abort it is missing; the Sandbox copy of the exact same file already has the fix. Second, every money amount parsed from an incoming payload across all six Map/Reduce integration scripts is de-commafied with .replace(",", ""), which only removes the first comma in a string — a value like "1,234,567.89" becomes "1,234567.89", which fails to parse as a number. This repeats at roughly 40 call sites across every money field this integration touches, and the correct global-replace pattern appears nowhere in the repo. A third pattern is heavy duplication: the same ~15 helper functions are copy-pasted across up to six separate large scripts instead of one shared module.

M-007 Consider · Open

getInputData materializes the full unprocessed-record list as an array rather than returning the search

⚠ What's wrong

Each integration script manually pages through its saved search in a loop and returns a plain array of ids, instead of returning the search object itself and letting the platform paginate natively. The manual pagination is implemented correctly and doesn't drop rows, so this is a style note, not a defect.

→ Recommended fix

Consider returning the search.Search object directly from getInputData, per Mason's own Map/Reduce pattern guidance for large datasets.

M-002 Must Fix · Open

Money amounts are de-commafied with a single-replace, silently corrupting any amount with two or more thousands separators

⚠ What's wrong

Every money value read from an incoming payload has its commas stripped with .replace(",", ""), which only removes the FIRST comma in JavaScript. An amount like 1,234,567.89 becomes 1,234567.89, which fails to parse as a number. This exact pattern repeats about 40 times across all six integration scripts, and the correct all-commas version never appears anywhere in the repo.

→ Recommended fix

Replace every single-comma .replace(",", "") on a money string with a global replace, .replace(/,/g, ''), or route all money parsing through one shared helper that does this correctly once.
